# Allocator API в Rust

## 🧩 Что такое Allocator API

**Allocator API** — это набор трейтов и типов, определяющих **как именно** Rust выделяет и освобождает память. Вместо жёстко зашитого системного `malloc` вы можете подставить **свой аллокатор** — глобально или локально для конкретной коллекции.

### 📜 Трейт `Allocator` (nightly, `allocator_api`)

```rust
pub unsafe trait Allocator {
    fn allocate(&self, layout: Layout) -> Result<NonNull<[u8]>, AllocError>;
    unsafe fn deallocate(&self, ptr: NonNull<u8>, layout: Layout);
    // ... + allocate_zeroed, grow, shrink (с дефолтными реализациями)
}
```

| Метод | Что делает |
|-------|-----------|
| `allocate` | Запрашивает блок памяти заданного размера и выравнивания (`Layout`) |
| `deallocate` | Возвращает блок обратно |
| `allocate_zeroed` | Как `allocate`, но обнуляет память |
| `grow` / `shrink` | Расширить/сжать существующий блок (для `Vec::push`) |

### 🆚 `GlobalAlloc` vs `Allocator`

| Трейт | Стабильность | Где используется |
|-------|--------------|------------------|
| **`GlobalAlloc`** | ✅ stable | Только через `#[global_allocator]` — один на всю программу |
| **`Allocator`** | 🟡 nightly (`allocator_api`) | Локально: `Vec<T, A>`, `Box<T, A>`, `HashMap<K, V, A>` |

`GlobalAlloc` — старый интерфейс, только для **глобальной** замены. `Allocator` — новый, позволяет **разные** аллокаторы для разных коллекций в одной программе.

## 1️⃣ Глобальный аллокатор (`#[global_allocator]`) — stable

Заменяет **все** аллокации Rust (`Vec`, `String`, `Box`, `HashMap`...) на выбранный аллокатор.

```rust
use mimalloc::MiMalloc;

#[global_allocator]
static MY_GLOB_ALLOC: MiMalloc = MiMalloc;   // имя любое, важен атрибут

fn main() {
    let v = vec![0u32; 10];   // ← аллокация через MiMalloc
    println!("v: {:?}", v);
}
```

**Требования:**
- Ровно **один** `#[global_allocator]` на программу.
- Тип должен реализовывать `GlobalAlloc`.
- Объявляется в **бинаре** (`main.rs`), не в библиотеке.
- Имя переменной — **любое** (`GLOBAL`, `MY_GLOB_ALLOC`, `A`...).

**Зачем:**
- `mimalloc`, `jemalloc`, `snmalloc`, `tcmalloc` часто дают **5–15% ускорения** на нагруженных сервисах без правки бизнес-кода.
- Меньше фрагментации, лучше масштабирование по потокам.

**Что НЕ покрывается:**
- Стек (`let x = 5;`).
- Статические данные.
- C-библиотеки (`libsqlite3`, `openssl`), вызывающие `malloc` напрямую.

## 2️⃣ Локальный аллокатор (`Allocator` API) — nightly

Позволяет привязать **конкретную коллекцию** к **конкретному аллокатору**.

```toml
[dependencies]
bumpalo = { version = "3.16", features = ["allocator-api"] }
```

```rust
#![feature(allocator_api)]   // нестабильная фича

use bumpalo::Bump;

fn main() {
    let arena = Bump::new();                              // локальная арена

    let mut v: Vec<i32, &Bump> = Vec::new_in(&arena);     // Vec, привязанный к арене
    v.push(10);
    v.push(20);
    v.push(30);

    println!("{:?}", v);
}   // арена уничтожается — вся память освобождается ОДНОЙ операцией
```

**Ключевое отличие от глобального:** тип коллекции меняется — `Vec<T, A>`, где `A` — тип аллокатора. Второй generic-параметр.

### 🎯 Когда нужны локальные аллокаторы

| Сценарий | Что даёт |
|----------|----------|
| **Arena / Bump** | Много мелких объектов, живут одинаково долго → освобождаются разом |
| **Парсеры, компиляторы** | AST, узлы дерева — всё в одной арене, `Drop` не нужен |
| **Embedded** | Контроль над каждым байтом, нет системного `malloc` |
| **Игры** | Покадровые аллокации — вся арена на кадр, сброс в конце |
| **Транзакции** | Откат = сброс арены |

## 🧱 Arena и Bump Allocator

**Arena (арена)** — область памяти, из которой:
- объекты выделяются **последовательно**,
- освобождение — **оптом**, сразу всей ареной.

**Bump Allocator (толкающий)** — частный случай арены с простейшей логикой:

```
[■■■■■■■■■■□□□□□□□□□□□□□□□□□□]
          ↑
        bump ↑ на size при каждом allocate
```

Указатель просто «подпрыгивает» вверх на размер блока. **`deallocate` — no-op**, память освобождается только при уничтожении всей арены.

**Плюсы:**
- Аллокация — это `ptr += size; ptr` (несколько инструкций).
- Нет фрагментации.
- Освобождение — O(1) на всю арену.

**Минусы:**
- Нельзя освободить отдельный объект.
- Память растёт до пикового использования.

**Крейты:** `bumpalo`, `typed-arena`, `id-arena`.

## 🔌 Встраиваемые системы (Embedded)

Микроконтроллеры (STM32, ESP32, AVR) и устройства с **килобайтами ОЗУ**:

- Нет ОС, нет `malloc` — только свой аллокатор.
- Часто `#![no_std]` + `alloc` crate + кастомный `GlobalAlloc`.
- Примеры: `embedded-alloc`, `linked_list_allocator`, `talc`.

```rust
#![no_std]
extern crate alloc;

use linked_list_allocator::LockedHeap;

#[global_allocator]
static ALLOCATOR: LockedHeap = LockedHeap::empty();

fn init_heap() {
    // отдаём аллокатору статический буфер под кучу
    unsafe { ALLOCATOR.lock().init(HEAP.as_mut_ptr(), HEAP_SIZE); }
}
```

Здесь **вся куча** — фиксированный массив в `.bss`, и аллокатор выдаёт из него блоки.

## 🎯 Практический вывод

1. **Начните с глобальной замены** — `mimalloc` или `jemalloc` через `#[global_allocator]`. Это 5–15% ускорения **бесплатно**, без правок бизнес-логики.

2. **Локальные аллокаторы** — если у вас:
   - парсер/компилятор с деревьями объектов,
   - игровой цикл с покадровыми аллокациями,
   - транзакции с откатом,
   - embedded.

3. **Arena/Bump** — когда объекты живут **одинаково долго** и освобождаются **вместе**. Тогда `Drop` не нужен, освобождение — одна операция.

4. **Embedded** — только свой аллокатор поверх статического буфера, `no_std` + `alloc`.

5. **Проверяйте эффект** — `perf`, `heaptrack`, `MIMALLOC_SHOW_STATS=1`, `criterion`. Не всякая замена аллокатора даёт выигрыш: на маленьких программах разница может быть в пределах шума.
